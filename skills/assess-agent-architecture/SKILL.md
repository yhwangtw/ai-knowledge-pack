# Agent 架構評估

## 目的與界線

回答「是否需要 Agent、目前有哪些證據、最小可行方案是什麼、什麼條件下可試行」。評估功能需求、資料風險、維運與離線可行性；不因為使用者提到 Agent 就預設採用多 Agent 或特定框架。本 Skill 不呼叫工具，也不把評估視為實際部署。

先讀 [閱讀契約](../../START-HERE.md)、[能力邊界](../../knowledge/01-boundaries.md)、[離線環境](../../knowledge/02-offline-enterprise.md)、[證據與風險](../../knowledge/03-evidence-and-risk.md)。

## 輸入契約

使用者提供：任務與成功定義、使用者、輸入／輸出、資料分級、讀／寫動作、容許的人工作業、頻率／容量、內外網邊界、模型部署聲明、工具證據、Nexus／Harbor 工件清單、維運限制與預算。可以只提供摘要；缺漏標未知。

不要求實際連線網址、認證值、真實客戶資料或未授權原始碼。使用者聲明「有 API」「模型在公司」不是本次連線與授權證明。

## 步驟

1. 將輸入編成 F-xx，區分已提供、假設、建議、未知。先判斷任務是產生建議、受控查詢還是變更狀態。
2. 先問最多三個會改變決策的缺漏問題。硬性禁止條件或未知模型部署／資料授權，不能靠權重評分抵銷。
3. 建立能力登錄：模型推論、讀檔／檢索、每一項讀取與寫入工具、工件取得。記錄狀態、證據時間、操作與權限範圍；未驗證就明說。可使用 [能力模板](../../templates/CAPABILITY-REGISTER.tsv)。
4. 至少比較三個不同複雜度的選項：
   - 一般程式或固定工作流；文字任務可附模板與核准模型。
   - 固定工作流搭配核准的本地檢索（若必要）。
   - 有步數、時間與成本上限的受控 Agent，僅在動態選擇步驟有價值時。
   說明每個方案解決什麼、代價、限制與淘汰條件。若考慮多 Agent，另外證明責任切分的價值、通訊／狀態成本與失敗隔離；沒有證據就不選。
5. 用政策與安全前提先篩選，再依品質、可重現性、延遲、維運、成本比較。加權分數須寫權重與計算，不以主觀分數假裝實測結果。
6. 描述候選資料流與信任邊界：人員／入口 → 權限檢查 → 已核准資料 → 推論 → 輸出驗證 → 人工審查。區分推論、檢索、工具、工件儲存；不把 Nexus／Harbor 當作模型推論 API。
7. 檢查無外連條件：模型與 tokenizer／執行庫、直接與間接套件、基礎映像與平台、授權、雜湊、掃描資料、信任根、內部身分服務、遙測與更新。缺件受阻，記錄核准匯入需求；不建議外部備援或自動下載。
8. 檢查提示注入、跨專案資料洩漏、身分傳遞、檢索 ACL、快取與日誌保存。模型文字不能取代執行器的權限控制。若涉及寫入，設計明確目標與授權、必要人工核准、最小權限、重複請求處理、停止條件與復原，但不執行。
9. 定義 PoC：固定且已核准的資料集、基線、品質／安全／效能指標、分母、通過門檻、失敗處理、上限與停止規則。不得把測試設計寫成已通過。
10. 算容量與成本時列公式與單位。沒有模型大小、token 速率、GPU 規格或尖峰負載就不猜硬體／金額。提供量測計畫，總成本包括人員、運算、維運與工件治理。
11. 提出採用、附條件試行、維持基線或暫緩的結論。把硬性阻擋、建議與責任角色分開，連到需求與證據。

## 輸出契約

使用 [評估模板](../../templates/AGENT-ASSESSMENT.md)，保留不適用的理由，至少含：

- 決策、範圍、證據／假設／未知與三個以內的問題。
- 任務分解、能力登錄與至少三種方案的比較。
- 建議資料流、模型／技能／工具邊界與授權控制。
- Nexus／Harbor 離線依賴與工件治理檢核。
- 風險與控制、成本容量、可觀察的 PoC 驗收。
- 阻擋事項、維運責任、停止／回復與再評估觸發條件。

## 自查

- 是否說明固定流程能否解決，並避免未經證明的多 Agent 複雜度？
- 沒有現場結果時，是否把模型／工具連線標為未驗證？
- 每個資料流都有權限與失敗處理，檢索先過濾授權資料，回傳前再次驗證？
- 是否分清 checkout 純文字文件、Nexus 工件、Harbor 映像與推論服務？
- 是否有安全硬門檻、量測分母、成本公式、循環上限與人工停止方式？
- 是否保留缺件、證據不足與資料衝突，不偷改外連政策？
