# PM 寫 PRD

## 目的與界線

產出供 PM、工程、設計與 QA 審查的 PRD 草案。不要把需求草案寫成已核准承諾、不要自行指定實際發布日期。本 Skill 不撰寫或執行程式、不連接任何服務，也不發布文件。

先讀 [閱讀契約](../../START-HERE.md)、[能力邊界](../../knowledge/01-boundaries.md)、[證據原則](../../knowledge/03-evidence-and-risk.md)。無外連情境涉及技術交付時，再讀 [企業離線說明](../../knowledge/02-offline-enterprise.md)。

## 輸入契約

使用者可提供零散文字；若有資料，優先包括：

- 產品／專案代稱、目標使用者與使用情境。
- 現行痛點與證據；目前流程與基準指標。
- 想達成的結果、候選需求與優先序。
- 資料分級、使用權限、內外網限制、既有系統與時程限制。
- 誰可以做決策，以及哪些內容已核准。

未提供就標示未知。不要要求原始客戶名單、個資、憑證或機密原文。模板中的空白代表待填，不能推論為公司已存在的設定。

## 步驟

1. 將輸入分段編成 F-01 等證據 ID。只抽取輸入明述的內容，分出已提供、假設、建議與未知。若輸入明示資料或匯出欄位，先逐項建立欄位清單：完整保留原名、明示順序、格式及限制，不省略、合併或擅自改名；型別、時區、空值與定義未給就逐格寫「待確認」。候選但未核准的欄位另列，不能混入必需輸出。可用 [欄位清單](../../templates/FIELD-INVENTORY.tsv)。
2. 一句話描述「誰在何時遇到什麼問題，造成什麼影響」。說明問題證據及未被證明的因果；不把使用者提出的功能當作問題本身。
3. 先列最多三個會改變範圍、成功定義或安全邊界的問題。可獨立撰寫的部分照常完成；未知的分母、角色或政策不能用數字編造。
4. 定義成果與指標。每個指標寫基準、目標、分子／分母或測量規則、期間與責任角色。缺基準時提出取得方法；目標未核准則標「建議」。
5. 列出 MVP 範圍與明確不做項目。使用 Must／Should／Could 或同等單一優先序；區分第一版必需與後續選項。
6. 每項需求設 R-xx，列使用者／動機、行為、資料／權限、失敗與例外處理、優先序、依賴與驗收 A-xx。離線、登入失敗、無資料、拒絕授權與重複請求要依情境覆蓋。
7. 寫正常與失敗流程，以可觀察結果描述驗收：前提、動作、結果、通過門檻。避免只寫「快速」「安全」「好用」。
8. 補非功能需求、資料保存、風險、上線前條件、停止與回復方式。Nexus／Harbor 只列為公司聲明的環境或依賴，不宣稱已連線、已備齊工件或功能已支援。
9. 建立需求到驗收的對照；列未知事項、責任角色與決策期限／事件。若政策衝突，保持待決策並說明哪些要求無法同時成立。
10. 用下列自查與驗收表檢視後輸出草案。

## 輸出契約

使用 [PRD 模板](../../templates/PRD.md)。保留其段落；不適用時註明理由。開頭寫版本、草案狀態、資料範圍與三個以內的關鍵問題。至少包含：

- 問題、使用者、證據、目標與衡量方式。
- 範圍與不做項目、需求表、正常／例外流程。
- 非功能條件、資料與權限、可量測驗收。
- 依賴與風險、需求追蹤、發布／停止條件、待決策清單。

即使輸入不足，仍輸出可用的骨架與明確阻擋點，不虛構客戶訪談、成功率、成本、公司政策或已核准里程碑。

## 自查

- 明示欄位逐項對照原始輸入，欄位數、名稱、明示順序與輸出格式完整保留；未知逐格標「待確認」，不得用常見慣例補造。
- 每個 Must 有至少一個驗收案例；權限拒絕與錯誤情況有可觀察結果。
- 指標分母與期間清楚；已提供的數字、計算與目標前後一致。
- 每個假設都有影響與驗證責任角色；未知與衝突沒有被寫成既成事實。
- 不在輸出中放入任何實際憑證，不要求外部查詢或安裝補件。
- 尚未實測的效能與工具能力標成目標／未驗證。

參考品質：[完全虛構的輸入](../../examples/pm-prd/input.md) 與 [完整 PRD 輸出](../../examples/pm-prd/output.md)。驗收使用 [測試題](../../tests/pm-prd/cases.md) 與 [驗收準則](../../tests/pm-prd/acceptance.md)；評測時先不要讀範例輸出或驗收答案。
